# 全球产业链图谱：架构与证据规范

> 状态：**第 0 层已落地**（495 节点，0 关系边）
> 入口：`/apps/supply-chain/`　中文名称：全球产业链　英文名称：Global Supply Chain
> 姊妹文档：`docs/SUPPLY_CHAIN_SOURCES.md`（物流通道层的来源与许可）

## 1. 目标与诚实边界

**目标**：以标普 500 成分股为骨架，呈现每家公司在全球产业链中的位置，并可下钻查看
单家公司的上下游关系网——点开苹果看它的供应商链条，点开英伟达看它的。

**边界必须一开始就说清楚**：完整、准确的公司级全球供应链关系数据**不存在免费版本**。
做这门生意的是 Bloomberg SPLC、FactSet Supply Chain Relationships、S&P Capital IQ /
Panjiva、LSEG、Sayari、Interos，年费以万美元计。

因此本板块交付的**不是「完整产业链」，而是「可证据化的产业链子集」**：每一条关系都
来自公开申报文件或企业自披露，都能点开核验。页面必须显示覆盖率，**永远不得宣称完整**。

这不是能力不足的托词，而是产品定位：**一张 500 条有出处的边，价值高于 5000 条来路
不明的边**。后者在金融语境下是负资产。

## 2. 最高优先级规则：无证据不上图

模型「知道」台积电给英伟达代工、富士康组装 iPhone。**但没有出处的行业知识不是数据
来源**。把这类记忆写进 `data.json` 就是对真实企业断言未经证实的商业关系——违反
`AGENTS.md` 关于数据真实性的规定，也是本板块唯一不可挽回的错误类型。

因此：

1. **每条边必须携带非空 `evidence[]`**，否则不得写入发布文件。这由生成脚本硬校验，
   不是靠自觉。
2. **`evidence` 必须可点开核验**：原始文件 URL、文件日期、在文件中的定位。
3. **`confidence` 只有两档**：`disclosed`（申报或自披露原文写明）与 `inferred`
   （由规则从公开数据推导，必须写明推导方法）。**不得混用，不得把 inferred 显示成
   已确认关系。**
4. **模型生成的文本不得作为任何一条边的 evidence。** 文本摘要只能描述已有的边，
   不能创造边。

## 3. 免费的一手证据源

| 证据类型 | 来源 | 能得到什么 | 可规模化 |
|---|---|---|---|
| 客户集中度披露 | SEC EDGAR 10-K（ASC 280 强制披露占营收 10% 以上的客户） | 「X 公司 22% 营收来自苹果」——**反向即得苹果的重要供应商** | 是，全体美股上市公司 |
| 企业自披露供应商名单 | 苹果年度供应商名单等 | 直接的供应商清单，含工厂位置 | 否，仅少数公司 |
| 冲突矿产 Form SD | SEC 强制申报冶炼厂／精炼厂清单 | 通向**上游矿产**那一段 | 部分，数百家制造业公司 |
| 子公司清单 Exhibit 21 | 10-K 附件 | 集团内部结构 | 是 |

EDGAR 全部为美国政府公有领域作品，**零许可风险、零费用**，与 `SUPPLY_CHAIN_SOURCES.md`
「只用政府作品口径」是同一条纪律。SEC 要求声明身份的 User-Agent 并限速每秒 10 次，
本仓库脚本远低于该上限，联系方式从环境变量读取，不硬编码个人邮箱。

### 3.1 定位命中 ≠ 能抽出边

大量公司只写「一家客户占营收 22%」而**不写是谁**。这类段落是线索，不是边。
`scripts/supply-chain/probe_edgar_relationships.py` 因此把「命中披露段落数」与
「其中点名了对方的段落数」**分开报告**——后者才决定实际能拿到多少条边。

## 4. 数据模型

```jsonc
// 节点：公司。骨架来自站内已日更的 apps/companies/sp500.json，不另建事实来源。
{
  "id": "AAPL",                    // 上市公司用代码；非上市供应商用规范化名称
  "cik": 320193,                   // SEC 实体标识，来自 EDGAR，边的锚点
  "sic": 3571, "sicDescription": "Electronic Computers",
  "stage": "brand-integration",    // 价值链阶段，见第 5 节
  "stageBasis": "sector-initial",  // ← 口径来源，初步口径必须自报家门
  "listed": true
}

// 边：关系。没有 evidence 就不发布，由生成脚本硬校验。
{
  "from": "AVGO", "to": "AAPL",
  "type": "supplier",              // supplier / customer / smelter / subsidiary
  "confidence": "disclosed",       // disclosed | inferred，不得混用
  "evidence": [{
    "sourceType": "sec-10k-customer-concentration",
    "url": "https://www.sec.gov/Archives/edgar/data/.../avgo-20251102.htm",
    "docDate": "2025-12-12",
    "locator": "Item 1A. Risk Factors，客户集中度段落",
    "quote": "One customer ... accounted for approximately 20% of our net revenue"
  }]
}

// 覆盖率：与数据同级发布，页面必须显示，不得省略。
{
  "coverage": {
    "claimComplete": false,        // 永远为 false
    "nodesTotal": 495, "nodesWithEdges": 0,
    "edgesBySource": { "sec-10k-customer-concentration": 0, "apple-supplier-list": 0 },
    "note": "本图谱只收录有公开出处的关系，不是完整供应链"
  }
}
```

逐条数据仍沿用全站 `dataMeta` 契约（`mode`/`status`/`source`/`asOf`/`updatedAt`/
`frequency`/`note`），不新造字段。

## 5. 价值链阶段：初步口径与后续校正

按方案 C：**先用板块级初步口径上线并明确标注，第 2 层真实关系边完成后用实际上下游校正。**

| 阶段 | 含义 |
|---|---|
| `upstream-resource` | 上游资源：能源、原材料开采与初加工 |
| `intermediate-manufacturing` | 中间制造：零部件、设备、资本品 |
| `brand-integration` | 品牌整合：面向终端的品牌与系统集成 |
| `distribution-service` | 分销服务：零售、物流、终端服务 |
| `platform-service` | 平台服务：软件、互联网、通信平台 |
| `supporting` | 支持性行业：金融、地产、公用事业，不在实物链上 |

**初步口径的诚实要求**：当前只有 GICS 一级板块（11 类）可用，粒度明显偏粗——同属
「科技」的英伟达与微软，产业链位置完全不同。因此：

- 每个节点带 `stageBasis` 标明口径来源：`sector-initial`（板块与阶段一一对应，已判定）／
  `sector-ambiguous`（板块横跨多段，只给候选集）／`sic-refined`（SIC 行业码细化）／
  `edge-derived`（真实上下游边反推）／`unknown`（板块不在映射表内）；
- 页面必须显示当前口径级别，**不得把板块级推断显示成公司级结论**；
- 第 2 层完成后逐节点升级 `stageBasis`，升级过程可见、可回退。

### 5.1 歧义板块不给结论，只给候选集

第 0 层首版曾给每个节点一个单一阶段并附 `stageAmbiguous` 标记。实测输出后否决了这个做法：
**苹果、英伟达、微软会同时被标成「中间制造」**——对微软和苹果都是错的。加了歧义标记也不行，
页面上出现「微软 = 中间制造」就是对一家真实公司的错误断言，与仓库「不用默认值静默覆盖
有效数据」的规则冲突。

现行做法：板块与阶段一一对应时才给 `stage`；横跨多段时 `stage` 为 `null`，改给
`stageCandidates` 候选集。

| 展示 | 是否可接受 |
|---|---|
| 微软 = 中间制造（附歧义标记） | ❌ 对真实公司的错误断言 |
| 微软 = 待细化（可能：中间制造／品牌整合／平台服务） | ✅ 数据实际支持的说法 |

代价是首版只有 **182/495（36.8%）** 节点有确定阶段，其余 313 个只给候选集。这个比例
本身就是有用的信息——它精确地量化了「板块级分类不足以定位产业链位置」，并会随 SIC
行业码与真实边落地而上升。`health.json` 的 `stageResolvedPct` 跟踪这条曲线。

## 8. 已建立的质量防线

- `scripts/validate_supply_chain_extraction.py`——离线校验抽取规则的定位、点名与误报，
  22 项断言。用例全部来自开发中的真实失败：单层限定词漏掉唯一会点名客户的句式；
  裸 `Co` 后缀把小标题 `Customer Concentration` 误抽成公司名；后缀不按长度排序时
  `Corp` 把 `Microsoft Corporation` 截断。抽取规则一旦退化，后果是**边指向错的公司**，
  比没有数据严重得多，因此这条防线先于抽取器存在。
- `scripts/supply-chain/probe_edgar_relationships.py`——实测 CIK 解析率、SIC 可得性、
  真 10-K 的规则命中率与点名率、全量运行耗时估算。**不实测就写抽取器是在赌。**
- `scripts/validate_supply_chain_graph.py`——发布侧契约校验，与生成脚本里的
  `assert_edge_contract()` 构成两道防线，针对同一件事：模型「知道」的行业关系不是数据
  来源。已用注入违规的方式实测拦截能力：无证据的边、证据缺 URL、非 https 出处、
  `confidence` 越界、板块级推断冒充公司级结论、宣称完整、空文件覆盖——7 项全部拦下，
  未改动的真实文件无误报。

## 8.5 首轮 EDGAR 实测结论（2026-09-02）

两次 Actions 机房实测（run #1 三家样本、run #2 十家样本）。**结论是负面的：按原设计的
全文正则抽取不可行，不得据此推进抽取器。**

### 基础设施：全部可用

| 项目 | 实测 |
|---|---|
| ticker → CIK 解析率 | **495/495 = 100%** |
| SIC 行业码 | 可得，且能区分 GICS 板块区分不了的公司（AAPL 3571 电子计算机 / NVDA 3674 半导体 / QCOM 3663 通信设备 / LRCX 3559 专用机械） |
| Form SD（冲突矿产） | 每家 5～13 份，第 3 层可行 |
| 10-K 取回 | 1.5～3.4MB，100～421ms |
| 全量估算 | 495 家 ≈ **9.6 分钟**，远低于 SEC 每秒 10 次上限 |
| `efts.sec.gov` 全文检索 | **可用**，返回 `hits` / `aggregations` |

### 抽取：不可行

10 家样本共定位到 **78 处**客户集中度披露段落，其中 **6 处**含公司名（7.7%）。
但逐条核对这 6 处后，**真正可用的只有 1 条**：

| 抽出的"公司名" | 实际是什么 |
|---|---|
| `QUALCOMM Incorporated.`（QCOM） | **申报人自己**，不是客户 |
| `Net The Company`（LRCX） | 表格标题噪声 |
| `Major Customers The Company`（LRCX） | 同上 |
| `Samsung Electronics Company`（LRCX，2 次） | **唯一真实的客户名**，且被截断（真实为 Samsung Electronics Co., Ltd.） |

**8/10 家公司一处都没点名**：AAPL、NVDA、AVGO、SWKS、JBL、GLW、MU、AMAT。

### 根因：不是正则写得差，是披露制度如此

ASC 280 要求披露重大客户的**存在与占比**，**不要求披露客户身份**。多数申报人刻意不写名字。
美光的原文就是标准写法：

> Revenue from one customer was 17% ... Revenue from one customer was 10% of total revenue

有金额、有占比、**没有名字**。这类段落是线索，不是边。

### 更危险的是误报

抽出的 6 条里有 3 条是噪声（申报人自己、表格标题）。**如果照此建边，会产出指向错误
公司的关系**——正是本文档第 2 节定义的唯一不可挽回的错误。探针在写抽取器之前拦下了它。

### 改道方向：全文检索反查

不再"逐家解析 10-K 指望里面有名字"，改为"**按已知大公司名反查谁提到它**"：
`efts.sec.gov` 已实测可用，对 `"Apple Inc."` 之类的名称在全体 10-K 里检索，命中方即为
声称与其有业务关系的申报人。这条路精度高得多，但需要单独探测其查询语法、结果上限与
误报率后才能判断，**未探测前不得推进**。

### 改道方向实测：反查也不成立（2026-09-02，run #5）

取样干净后（命中 100 条 → 排除目标自身申报 92 条、附件 1 条 → 可分析 7 条）：

**7 份原文共 77 处提及 —— 客户语境 0 处（0.0%）、诉讼 18 处、其他 59 处。**

分析到的公司是谁，比数字更说明问题：

| 申报人 | 提及 | 性质 |
|---|---|---|
| VirnetX Holding（×3 年） | 21 / 17 / 21 | 专利诉讼方，每份 6 处诉讼语境 |
| Voip-pal.com（×2 年） | 4 / 2 | 专利诉讼壳公司 |
| Orchard Enterprises | 12 | 无供应关系语境 |
| Wireless Attachments | 0 | 主文档里根本没提及 |

**根因：全文检索按相关性排序，而相关性≈词频。提「Apple Inc.」最多的是起诉苹果的人，
不是供应苹果的人。** 真实供应商在 10-K 里只会提一两次（客户集中度附注里），专利诉讼方
会提二十次。排序天然把噪声推到最前。

`entity_filter` 聚合给出的候选名单同样是混合物——真实关联方（Liquidmetal 独家授权、
Intel、Qualcomm）、渠道（Verizon）、纯诉讼方（VirnetX）、平台开发者（Glu Mobile）、
专利授权方（InterDigital）混在一起，且**无法从申报文本本身可靠区分**。

### 两条路都实测否决后的结论

| 方案 | 实测产出 | 判定 |
|---|---|---|
| 正查：逐家解析 10-K 找客户名 | 78 处披露 → 1 条真实边 | 否决 |
| 反查：按名搜谁提到目标 | 77 处提及 → 0 条客户语境 | 否决 |

**SEC 申报文件不系统性地编码供应商关系。** 这不是方法问题——商业产品之所以年费以万
美元计，正是因为它们建立在人工策展、进口提单和专有数据源之上，而不是靠解析公开申报。

因此「点开苹果看完整产业链」**无法从免费 SEC 数据规模化实现**。仍然可做的是：

1. **第 0 层已交付**：495 节点 + 价值链阶段，可用 SIC 行业码把 313 个待细化节点升级；
2. **Form SD 冲突矿产**：每家 5～13 份，含冶炼厂／精炼厂名单，是**结构化且真实**的
   上游来源——尚未探测其内容格式；
3. **企业自披露供应商名单**：苹果等少数公司发布，入口待找；
4. **小规模人工策展**：逐条挂出处，数量有限但每条可核验。

**不可做**：用模型记忆补全关系、把「提到」当成「供应关系」、把覆盖率不足说成完整。

### 苹果供应商名单：仍未找到

三个候选页面（`apple.com/supplier-responsibility/`、`apple.com/supply-chain/`、
`investor.apple.com/esg/`）分别返回同一个 550KB 落地页或 404，页面全文里唯一的 PDF 是
《供应商行为准则》，不是年度供应商名单。第 1 层起点需要另找入口。

## 8.6 SIC 升级实测结果（2026-09-02）

按 A+B 方案，先用 SEC 的 SIC 行业码升级第 0 层的阶段判定。

**已判定阶段：182/495（36.8%）→ 495/495（100%）**，全部 313 个只能给候选集的节点被解决。
`stageBasis` 实际分布：`sic-refined` 495。

| 公司 | SIC | 阶段 | GICS 板块能否分辨 |
|---|---|---|---|
| 苹果 | 3571 电子计算机整机 | 品牌整合 | ❌ 同为「科技」 |
| 英伟达 | 3674 半导体 | 中间制造 | ❌ 同为「科技」 |
| 微软 | 7372 预装软件 | 平台服务 | ❌ 同为「科技」 |
| 埃克森美孚 | 2911 石油炼制 | 上游资源 | ✅ |
| 特斯拉 | 3711 整车制造 | 品牌整合 | ❌ 同为「可选消费」 |
| 沃尔玛 | 5331 杂货零售 | 分销服务 | ❌ 同为「必需消费」 |

各环节公司数：中间制造 142、支持性行业 139、分销服务 75、平台服务 60、品牌整合 57、
上游资源 22。

### 实测中修掉的两个真错

1. **33xx 整段归为冶炼**会把康宁（SIC 3357 有色线材拉制）误判成上游资源——它做的是
   玻璃基板与光纤，是不折不扣的中间投入。改为 3300-3349 冶炼精炼（上游）、
   3350-3399 轧制拉制铸造（中间制造）。
2. **`coverage.stageByBasis` 把 495 个 `sic-refined` 节点全报成 `sector-initial`**，
   等于把 SIC 升级的功劳记在板块级口径头上、低报了数据质量的真实来源。校验器当时
   只核对 `sector-ambiguous` 一项，所以没拦下——已改为逐项核对，修好后立刻抓到了这个错报。

### 各产业链环节今日表现（B 方案）

`nodes.json` 新增 `stagePerformance`：按环节汇总当日涨跌，**等权与市值加权并列给出，
不互相冒充**。阶段未判定的公司不摊入任何环节、过期报价不计入均值，两者单独计数。
行情值沿用站内 `sp500.json`，未重算、不另建事实来源。

## 8.7 Form SD 实测：第一批具名上游实体（2026-09-02）

正查与反查都否决后，Form SD 冲突矿产申报是**唯一实测产出具名实体**的来源。

| 公司 | 冲突矿产报告 | 大小 | 表格行 | RMI 冶炼厂编号 |
|---|---|---|---|---|
| 应用材料 AMAT | `cmrcy2025_final.htm` | 510KB | 366 | **325 个** |
| 英伟达 NVDA | `a2026conflictmineralsrepor.htm` | 278KB | 407 | 名单在，未用 CID 格式 |
| 苹果 AAPL | 未检出 | — | — | 探针只取前 2 个候选文档，CMR 附件排在后面 |
| 博通 AVGO | 未检出 | — | — | 同上 |

**2/4 检出，合计 325 个可识别的 RMI 编号。**

### 为什么这条路和前两条不同

| | 客户集中度（正查） | 全文反查 | Form SD |
|---|---|---|---|
| 披露是否强制具名 | ❌ 只需披露占比 | — | ✅ 须列出冶炼厂 |
| 实体标识 | 无，只有公司名字符串 | 无 | ✅ **RMI CID 全球统一编号** |
| 实测产出 | 78 处披露 → 1 条边 | 77 处提及 → 0 条 | 325 个具名实体 |

**CID 编号是关键**：实体按编号规范化，不必靠名字匹配——正好避开本项目踩过两次的
「同一实体多种名称写法」问题（`Apple Inc.` vs `APPLE INC`）。且不同公司的名单可以
交叉比对：同一个 CID 出现在多家申报里即为共同上游。

### 边的语义必须如实标注

Form SD 名单表示的是**「该冶炼厂出现在申报人的供应链中」**，而且是**间接的、不含份额、
不含层级**的。建边时必须写清楚这层含义，**不得表述为「X 是 Y 的供应商」**——申报人
自己通常也说明其信息来自逐级问询而非直接采购关系。

### 下一步

1. 修探针的文档筛选：列全部文档而不是前 6 个，候选不限于前 2 个（苹果、博通的 CMR 漏检）；
2. 解析 CMR 表格结构，确认冶炼厂名、CID、矿种、国别四个字段能否稳定抽出；
3. 抽取器输出必须逐条挂 `evidence`（申报 URL + 文件日期 + 表格定位），通过发布侧契约校验。

## 8.8 Form SD 覆盖率实测：申报强制，名单不强制（2026-09-02）

修完文档筛选后复测 6 家（run #8）。**结论：3/6 家的 Form SD 里有冶炼厂名单，
合计 519 个 RMI 编号。**

| 公司 | 冲突矿产报告 | 大小 | 表格行 | RMI 编号 |
|---|---|---|---|---|
| 应用材料 AMAT | `cmrcy2025_final.htm` | 510KB | 366 | **325** |
| Skyworks SWKS | `exhibit101-cmr2025.htm` | 264KB | 239 | **194** |
| 英伟达 NVDA | `a2026conflictmineralsrepor.htm` | 278KB | 407 | 名单在，未用 CID 格式 |
| 特斯拉 TSLA | `tm2615395d1_ex1-01.htm` | **42KB** | 13 | **0** |

### 关键发现：Form SD 强制申报，但不强制在申报里列出名单

特斯拉的报告只有 42KB、13 个表格行，命中了 `smelter or refiner` / `SOR` /
`Responsible Minerals Initiative` 等线索，**但没有实际名单**——它描述的是尽职调查
流程，不是冶炼厂清单。这不是探针筛错，是申报实践的真实差异。

因此第 3 层的覆盖率注定不是全量：**约半数公司会在 Form SD 里附完整冶炼厂名单，
另一半只写流程**。建边时必须如实披露这一点，不得把「有名单的公司」的覆盖率说成
全体标普成分股的覆盖率。

### 修掉的两轮筛选缺陷

1. **只看文档清单前 6 个**。EDGAR 每次申报都带系统文件（index / .txt / brokers /
   companysearch），排在最前，把真实文档整个遮住。
2. **从索引页 HTML 刮 href**。这会抓到 EDGAR 的站点导航链接——`privacy.htm`、
   `search.htm`、`oacq.htm`、`howinvestigationswork.html` 等九个，它们不在申报目录
   下、请求一律 404，按字母序还排在真实文档前面。特斯拉的报告排第 9 位，探测名额被
   这些垃圾用光，一次都没探到。

**用黑名单滤这些名字治标不治本——名单会变。** 改为读 EDGAR 每个申报都提供的
`index.json`：权威文件清单，不含站点导航，且带文件大小。名单动辄几百行，报告一定是
最大的那份，按体积倒序探测最省请求也最不会漏。修复后特斯拉的文档从 11 个降到 2 个
真实文档，报告排第一位被正确探测。

## 8.9 单家公司视图上线（2026-09-02）

`/apps/supply-chain/company.html?symbol=AAPL` —— 从产业链页面的公司表点公司名进入。

### 今天填的是什么

| 内容 | 来源 | 真实性 |
|---|---|---|
| 身份、市值 | 站内公司榜 | ✅ |
| 环节判定与依据 | SEC 官方 SIC 行业码 | ✅ 附申报链接 |
| 同行业公司（同 SIC） | 节点表推导 | ✅ 苹果 → 戴尔、Supermicro |
| 同环节公司数 | 节点表推导 | ✅ |
| 供应链关系边 | — | **0 条** |

### 空的时候怎么说

这一页今天没有任何关系边，因此它的核心不是「展示关系」，而是**说清楚有什么、没有什么、为什么没有**：

- 顶部直接写「本页尚未收录任何供应链关系」，不含糊；
- 层级卡逐层标注：一级／二级供应商标 `无数据源`，冶炼厂标 `来源可得`；
- 点开任一层，右栏给出**这一层为什么空**的具体原因（ASC 280 不要求写客户名、全文反查被诉讼方淹没）；
- 地理分布视图不画空地图，改为说明「需要关系数据，目前 0 条可定位」，并说明 Form SD 带国别字段、抽取器落地后即可启用。

### 视觉语言（与主页面一致）

**虚线 = 待接入，实线 = 已核验，选中只改颜色深浅、绝不改线型。** 选中若把虚线变实线，
等于用户点一下占位项它就「看起来被验证了」——这条已固化为浏览器契约断言。

### 手机降级

窄屏（≤560px）不给辐射图——SVG 在 360px 下信息密度过低，直接隐藏，只保留层级卡与出处栏。
桌面优先是项目所有者的明确取舍。

## 8.10 抽取器落地：第一批真实关系边（2026-09-02）

`extract_form_sd.py` 从 Form SD 冲突矿产申报里抽出冶炼厂关系边，写到
`apps/supply-chain/edges/<代码>.json`，由 `nodes.json` 的 `edgeIndex` 索引。
这是本板块第一批有出处的企业间关系。

### 边的语义（页面必须照这个措辞）

**「该冶炼厂出现在申报人的供应链中」——间接、不含份额、不含层级。**
不是直接供货关系。申报人自己也不知道中间隔了几层。浏览器契约里有一条断言专门
守这个：页面不得出现把冶炼厂说成该公司供应商的措辞。

### 两类条目，分开统计

| 类型 | 标识 | 跨申报人合并 |
|---|---|---|
| `rmi-cid` | RMI 全球统一编号（CID000082） | 可靠，按编号 |
| `name-only` | 只有厂名 | 只能按名字规范化，写法不同就会重复 |

`_slug()` 只统一大小写与标点，**不做同义合并**：`Aurubis AG` 与 `Aurubis AG, Hamburg`
保持两条。宁可一家重复出现，不可两家被错并成一家。页面与登记表都分开报这两个数。

### 解析规则：按内容识别，不按列序

各家表头不一样（`Metal / Smelter Name / Smelter ID / Location` 与
`Smelter ID / Country / Standard Smelter Names / Metal` 都真实存在）。按第几列取值必然
在某一家上错位，因此改为：哪个格子含 CID 就是编号，是已知国名就是国别，整格是矿种词
就是矿种，剩下最长的才是厂名。认不出的字段留 `null`，不猜。

收一行的条件是**矿种 + 厂名 + 国别齐全**（有 CID 则只需 CID）。

### 实测踩过的五种假名单与真名单（都已固化为离线夹具）

| 形状 | 实例 | 处理 |
|---|---|---|
| 标准四列带编号 | 应用材料 325 家 | ✅ 收 |
| 无编号但三要素齐全 | 英伟达 238 家、英特尔 208 家 | ✅ 收，标 name-only |
| 纯国名附录（三列全是国名） | 微软 274 行 | ❌ 不收，也不算漏收 |
| 国别 × 矿种矩阵 | 英特尔 243 行 | ❌ 有国名有矿种但没有厂名列 |
| 厂名带脚注星号 | 英特尔全表 `A.L.M.T. Corp.*` | ✅ 剥掉星号再入库 |
| 排版用嵌套表 | 多家 | ✅ 栈式解析，不用正则切 `<tr>` |

**这一节的每一行都是我先判错、再被诊断纠正的。** 第一版规则「只认 CID」把英伟达
整份真名单丢掉；第一版「漏收行」启发式又把微软与英特尔的国名表数成漏收的冶炼厂，
方向正好是自我夸大。两次都是先看被丢弃行的原始内容才发现的——
**不看原始数据就改规则，等于用假设换假设。**

### 不拿坏结果覆盖好数据

1. 本轮拿到的公司数低于磁盘已有的 60% → 判定整轮异常，一个字都不写；
2. 单家取数失败 → 保留它已有的边文件，不删；登记表与索引一律从磁盘重建；
3. 内容没变（只有时间戳不同）→ 不重写。Form SD 一年一报，天天刷时间戳会在仓库里
   堆出没有信息量的 diff，还会让「今年名单变了没有」在历史里查不出来。

### 全量实测结果（495 家，2026-09-02）

| 状态 | 家数 |
|---|---|
| 有冶炼厂名单 | **85** |
| 有申报、正文未列名单 | 149 |
| 从未申报 Form SD | 256 |
| 取数失败 | 5 |

产出 **20,245 条边**、边文件与登记表合计 6.2 MB。条数最多的是丹纳赫系工业件与
连接器厂商：多佛 782、安费诺 698、罗克韦尔 691、美敦力 599、泰科电子 472。

Form SD 强制**申报**，不强制在申报里**列名单**——149 家有申报却没有可解析的名单
（苹果、博通、通用、特斯拉都在其中）。这三种状态在 `smelters.json` 的 coverage 里
分开计数，**不能把「有申报无名单」并进「无申报」**——那是把披露制度的上限说成抓取
失败。覆盖率因此注定不是全量，页面上如实写出三个数。

### 「1713 家冶炼厂」是条目数，不是实体数

登记表有 1713 个条目（带编号 837、仅名字 876），但其中 **681 条无编号条目与某条
带编号条目名字完全一致**——78% 的无编号条目其实是同一家。直接报 1713 会把约 1032
家说成 1713 家。

处理办法是**记录事实、不做合并**：同名的条目挂 `sameNameAs` 指向那条带编号的，
coverage 同时给出三个数——`uniqueSmelters`（条目数）、`exactNameMatchWithCid`（同名
条目数）、`distinctAfterExactNameMatch`（扣掉同名后的**下限**）。真实数目在下限与
条目数之间：写法不同但其实同一家的（`Aurubis AG` / `Aurubis AG, Hamburg`）仍算两条，
因为没有编号就无从判断。发布侧校验器逐条核对这三个数与实际条目的一致性。

### 还没解决的

- 微软那份申报里另有约 100 行有厂名有国别但缺矿种，表内小标题没识别出来。
  **不猜矿种**：这些行不收录，页面上如实显示「未收录的行 N 行」并说明原因。
  解析器已加诊断（打印被丢弃行上方最近的表外文字），下一轮据此判断，不继续猜。
- 苹果、博通、通用的冲突矿产报告正文里没有表格（博通那份 27KB、`<table>` 计数为 0），
  名单可能在公司自己网站或 PDF 附件里。未追。
- 本轮 5 家取数失败，但这一轮的 `failedSymbols` 字段是事后补的，**这 5 家的代码只
  存在于当次运行日志里**，数据文件查不到。下一轮起会写进 coverage。
  「失败 5 家」而不说是哪 5 家，等于没人能去核对。
